# Metrics dashboards

A `metrics-dashboard` block combines numeric cards, time-series charts, and a latest-value table in one note, with shared date, target, and metric controls.
Open it in the live [[Web workspace]] or Native app connected to the same vault.
Static exports display a snapshot of the panels resolved when the site is built.
Shared filters and refresh require a live reader; chart tooltips and legends remain available on the published page.

Use this for service health, personal measurements, business figures, or financial indicators.
track displays metric data; the tool producing that data owns collection and calculations.
For example, track-finance can supply stock indicators to the same dashboard.

See [[Charts]] for standalone charts and [[Home dashboard]] for recent-note, journal, and pinned-link widgets.
Those home widgets use the separate `dashboard` fence.


## Published example

This dashboard uses the synthetic CPU readings below.
On this published site it shows all targets and dates at build time: web-a is **55.0 %**, web-b is **85.0 %**, and the chart and table use those same samples.
The panels use the same renderer as the live workspace. Hover over the chart or toggle its legend to inspect the published series.
Updating a published snapshot requires rebuilding the site; no live vault connection is needed to view it.

```metrics-dashboard
{
  "title": "CPU overview — synthetic sample",
  "panels": [
    {
      "type": "stat", "title": "Latest CPU",
      "gridPos": {"x": 0, "y": 0, "w": 8, "h": 8},
      "datasource": {"type": "track", "uid": "help-cpu.jsonl"},
      "targets": [{"expr": "cpu_usage", "legendFormat": "{{entity}}"}],
      "fieldConfig": {"defaults": {
        "unit": "percent", "decimals": 1,
        "thresholds": {"mode": "absolute", "steps": [{"value": null}, {"value": 80}]}
      }}
    },
    {
      "type": "timeseries", "title": "CPU history",
      "gridPos": {"x": 8, "y": 0, "w": 16, "h": 8},
      "datasource": {"type": "track", "uid": "help-cpu.jsonl"},
      "targets": [{"expr": "cpu_usage", "legendFormat": "{{entity}}"}],
      "fieldConfig": {"defaults": {"unit": "percent", "min": 0, "max": 100}}
    },
    {
      "type": "table", "title": "Latest CPU by target",
      "gridPos": {"x": 0, "y": 8, "w": 24, "h": 7},
      "datasource": {"type": "track", "uid": "help-cpu.jsonl"},
      "targets": [{"expr": "cpu_usage"}],

```


## Create a working sample

Use a track build with `metrics-dashboard` reader support, and start in the root of the vault where you want the sample.
These are synthetic CPU readings, not a connection to a real service.
Create `data/help-cpu.jsonl`, with one metric sample per line:

```sh
mkdir -p data
cat > data/help-cpu.jsonl <<'JSONL'
{"version":1,"name":"cpu_usage","entity":"web-a","time":"2026-09-18T12:00:00Z","value":40}
{"version":1,"name":"cpu_usage","entity":"web-b","time":"2026-09-18T12:00:00Z","value":65}
{"version":1,"name":"cpu_usage","entity":"web-a","time":"2026-09-19T12:00:00Z","value":55}
{"version":1,"name":"cpu_usage","entity":"web-b","time":"2026-09-19T12:00:00Z","value":85}
JSONL
```

Save this configuration as `help-cpu-dashboard.json` in the same directory:

```json
{
  "title": "CPU overview — synthetic sample",
  "panels": [
    {
      "type": "stat", "title": "Latest CPU",
      "gridPos": {"x": 0, "y": 0, "w": 8, "h": 8},
      "datasource": {"type": "track", "uid": "help-cpu.jsonl"},
      "targets": [{"expr": "cpu_usage", "legendFormat": "{{entity}}"}],
      "fieldConfig": {"defaults": {
        "unit": "percent", "decimals": 1,
        "thresholds": {"mode": "absolute", "steps": [{"value": null}, {"value": 80}]}
      }}
    },
    {
      "type": "timeseries", "title": "CPU history",
      "gridPos": {"x": 8, "y": 0, "w": 16, "h": 8},
      "datasource": {"type": "track", "uid": "help-cpu.jsonl"},
      "targets": [{"expr": "cpu_usage", "legendFormat": "{{entity}}"}],
      "fieldConfig": {"defaults": {"unit": "percent", "min": 0, "max": 100}}
    },
    {
      "type": "table", "title": "Latest CPU by target",
      "gridPos": {"x": 0, "y": 8, "w": 24, "h": 7},
      "datasource": {"type": "track", "uid": "help-cpu.jsonl"},
      "targets": [{"expr": "cpu_usage"}],
      "fieldConfig": {"defaults": {"unit": "percent", "decimals": 1}}
    }
  ]
}
```

Generate the note body and create a note in this vault:

```sh
TRACK_VAULT="$PWD" track metrics dashboard --dashboard help-cpu-dashboard.json --out help-cpu-note.md
TRACK_VAULT="$PWD" track new --title "CPU dashboard sample" < help-cpu-note.md
TRACK_VAULT="$PWD" track web
```

Open **CPU dashboard sample** in the workspace, or open that note in the Native app connected to this vault.
The generated Markdown contains one `metrics-dashboard` fence wrapping the JSON.
You can also paste that fence into an existing note; edit its JSON to change the panels.
The CLI validates the configuration and referenced data before writing the Markdown file; it does not itself create the note.

With all targets selected, the final values are **55.0 %** for `web-a` and **85.0 %** for `web-b`.
Select `web-b`: the card and table show 85.0 %, the card reports its 80.0 % threshold, and the chart keeps only that target.
Set **To** to `2026-09-18` to see 65.0 % instead.


## Shared controls and updates

| Control or display | Meaning |
| --- | --- |
| From / To | Restrict every panel to the selected period. Date-only bounds include the whole UTC day; an empty bound is unrestricted. |
| Target | Select one exact `entity`, or all targets. |
| Metric | Select one exact metric `name`, or all metrics. Panels for other metrics become empty. |
| Reset | Clear all shared filters. |
| Refresh | Reread local data. It does not contact an external service or calculate indicators. |
| Latest sample | The newest selected data timestamp, not the time Refresh was clicked. Each value also retains its own sample timestamp. |

Stat and table panels show the latest value **per series within the selected period**.
They do not sum targets or compute averages.
A series is identified by its data file, metric name, and entity.
Panel matchers such as `cpu_usage{entity="web-b"}` still apply when shared filters are selected.
An empty selection shows no data, not a zero or a value from another period.

Changes to files in the vault's `data/` directory trigger a dashboard reload in live readers.
The process that collects measurements must write those updates; track does not schedule collection.
Thresholds label numeric bands and can appear as chart lines. They do not send notifications or run alert rules.


## Adjust the panels

- Use `stat`, `timeseries`, or `table` for each panel's `type`.
- Place panels with `gridPos` on a 24-column grid: `x` and `y` start at zero, `w` is width, and `h` is height. Keep `x + w` at most 24. Without a position, a panel takes a full-width row. Narrow readers stack the panels.
- Set `datasource.uid` to a bare JSONL filename under this vault's `data/`, not an absolute path or an asset path. The note keeps a reference to that file; it does not copy the samples into its body.
- Set `targets[].expr` to a metric name, optionally followed by equality label matchers. This is a supported subset, not general PromQL.
- Set `fieldConfig.defaults.unit` to `percent` for values such as 85, or `percentunit` for fractions such as 0.85. `bytes` adds B; `none` and `short` omit the suffix. Other units, such as `ms`, are literal suffixes. Automatic SI abbreviation is not provided.
- Set `decimals` from 0 to 8. `min` and `max` set chart axis bounds. Absolute `thresholds.steps` define numeric bands; `null` is the baseline. Colors and value mappings from Grafana are not applied.

Each data record needs a metric `name`, a parseable date or RFC3339 `time`, and a finite numeric `value`; `entity` distinguishes targets.
Duplicate timestamps for the same series in one file are rejected.
Unlike the ordinal-time examples in [[Charts]], dashboard timestamps must describe actual dates or instants.


## Missing data and supported scope

If one panel reports a data error, check its filename and JSONL records; other valid panels remain usable.
For an empty panel, clear the shared filters and check the metric name, entity, and dates.
Invalid configuration or a reversed date range produces a dashboard error.

Grafana JSON is accepted only for the fields and panel types described here.
There is no drag-and-drop layout editor, template-variable support, transformation pipeline, general query engine, or reduction other than the latest value.
Unsupported panel types and reductions are rejected.

Existing `viewspec` chart notes still work.
New `track metrics dashboard` output uses `metrics-dashboard` to retain layout and shared controls.
`track render` continues to take View Spec or article JSON; it does not take dashboard JSON.

See [[CLI##Metrics]] for the related ingestion and alert commands.
